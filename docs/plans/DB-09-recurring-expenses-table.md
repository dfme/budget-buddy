## Entscheide

Vier Punkte liessen die ACs offen; alle vier sind mit dem User bestätigt.

- **`first_detected_month` als `TEXT` im Format `YYYY-MM`.** Der Wert *ist* ein Monat, kein Datum.
  Eine `DATE`-Spalte erzwingt die Konvention «immer der 1.», die nichts durchsetzt und die jede
  Abfrage kennen müsste. Das Projekt spricht ohnehin durchgängig `YYYY-MM` — `MonthParser`, alle
  Month-Endpoints, und `TransactionRepository.findDistinctExpenseMonths` formatiert dafür sogar
  mit `to_char(…, 'YYYY-MM')` zurück. Der lexikografische Vergleich ist für dieses Format
  korrekt; darauf baut das Frontend heute schon (`month <= currentMonth()`).

  **Bewusst ohne CHECK auf das Format**, obwohl `status` eine bekommt: Das Format ist eine
  Eingabevalidierung, und die hat das Projekt an der Systemgrenze (`MonthParser`, `InvalidMonthException`).
  `status` dagegen ist eine geschlossene Wertemenge, die das Schema kennt — siehe unten.

- **`UNIQUE (user_id, payee_key)`.** US-08 verlangt, dass «Kein Abo» dauerhaft wirkt, und
  `BE-REC-02` setzt dafür `status = 'DISMISSED'`. Ohne Eindeutigkeit könnte `BE-REC-01` beim
  nächsten Import eine zweite `DETECTED`-Zeile für denselben Empfänger daneben schreiben — der
  Ausschluss wäre umgangen, und zwar still. Die Constraint macht das strukturell unmöglich statt
  es dem Service zu überlassen.

  Die Constraint legt zugleich den Index an, den beide Endpoints brauchen: ihr `user_id`-Präfix
  bedient das `GET /api/recurring-expenses` aus `BE-REC-02` mit. **Kein zusätzlicher Index** auf
  `user_id` allein — der wäre reine Schreiblast ohne eigenen Nutzen.

- **`status TEXT` mit `CHECK (status IN ('DETECTED', 'DISMISSED'))`.** Der AC zählt die erlaubten
  Werte ausdrücklich auf. Das ist der Unterschied zu `notifications.type` (V10), das laut eigenem
  Kommentar mit künftigen Quellen *wachsen soll* und deshalb bewusst offen bleibt. Eine
  geschlossene Menge gehört in die Datenbank: sonst ist ein Tippfehler im Service eine stille
  Datenmutation, die niemand bemerkt. Erste CHECK-Constraint im Projekt; ein dritter Status wäre
  damit eine Migration — was für eine Zustandsmaschine die richtige Hürde ist.

  Verworfen: ein Postgres-`ENUM`-Typ. `CREATE TYPE` kommt im Projekt nirgends vor und macht jede
  Erweiterung zu einem `ALTER TYPE`.

- **Spaltenname `amount`, nicht `betrag`.** AC 2 und `us-08-09-12-breakdown.md:58` nennen ihn
  englisch, und `V10` (notifications) ist durchgängig englisch. Die älteren Tabellen
  (`transactions`, `fixed_costs`) tragen `betrag` — die Inkonsistenz ist damit vorbestehend und
  wird hier nicht aufgelöst, sondern dem AC folgend fortgeschrieben.

Übernommen aus dem bestehenden Muster, nicht neu entschieden:

- **`user_id`-FK ohne `ON DELETE CASCADE`**, wie alle anderen Tabellen seit DB-07 (#142): Die
  Kontolöschung (US-02, nDSG) bleibt eine bewusste, testbare Operation im Code statt einer
  stillen Fremdschlüssel-Nebenwirkung. Siehe «Löschpfad» unten.
- **`amount` als `DECIMAL(10,2)`** — niemals Gleitkomma (ADR-9).
- **`TEXT` statt `VARCHAR(n)`** für `payee_key`: in Postgres verhaltensgleich, ohne die Erwartung
  einer Längenangabe. Empfängernamen aus Bank-PDFs sind unbegrenzt lang (Begründung aus V02).
- **`id BIGINT GENERATED BY DEFAULT AS IDENTITY`** und **`created_at TIMESTAMPTZ DEFAULT now()`**
  wie in V10.

Alle Spalten sind `NOT NULL`: keine trägt zum Insert-Zeitpunkt eine sinnvolle Leere. Das
unterscheidet die Tabelle von `notifications`, wo `reference_id` und `read_at` bewusst nullable
sind.

## `payee_key`-Normalisierung (AC 3)

Werte werden ausschliesslich in Grossschreibung gespeichert, verglichen wird über `upper()` auf
beiden Seiten — wörtlich dieselbe Lösung wie `category_lookup` (V04), samt demselben Grund:
Postgres kennt das `COLLATE NOCASE` der SQLite-Zeit nicht, und eine DB-Extension dafür wollte
DB-05 nicht einführen.

Durchsetzen wird das der Service (`BE-REC-01`), so wie `CategoryLearningService` es für V04 tut.
Das Schema hält den Vertrag als Kommentar fest; erzwingen kann es ihn ohne Extension nicht.

## Löschpfad (US-02, nDSG)

`recurring_expenses` ist ab dieser Migration eine weitere abhängige Tabelle am User.
`UserService.deleteUser` (`backend/src/main/java/com/budgetbuddy/auth/UserService.java:183`) kennt
heute nur `TransactionCleanupPort` und `FixedCostCleanupPort` — sobald `BE-REC-01` die erste Zeile
schreibt, scheitert eine Kontolöschung an `recurring_expenses_user_id_fkey`.

Das ist derselbe Befund, den menschliches Review auf PR #272 für `notifications` nachgestellt hat.
Wie dort gibt es in einem reinen Schema-Vorlauf keinen Anknüpfungspunkt für einen
`RecurringExpenseCleanupPort` — es existiert noch keine Entity. Die Verpflichtung wird deshalb als
**AC an #253 (BE-REC-01)** verankert, wo die Entity entsteht, und im PR-Body dieses Tasks benannt.

## Schema

```sql
CREATE TABLE recurring_expenses (
    id                   BIGINT        GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id              BIGINT        NOT NULL,
    payee_key            TEXT          NOT NULL,
    amount               DECIMAL(10,2) NOT NULL,
    status               TEXT          NOT NULL
        CHECK (status IN ('DETECTED', 'DISMISSED')),
    first_detected_month TEXT          NOT NULL,
    created_at           TIMESTAMPTZ   NOT NULL DEFAULT now(),
    FOREIGN KEY (user_id) REFERENCES users(id),
    UNIQUE (user_id, payee_key)
);
```

## Test-Strategie

`RecurringExpensesMigrationTest` (`@SpringBootTest` gegen Testcontainers-Postgres 18, eine
Datenbank pro Testklasse — `PostgresTestDatabase`). Jedes AC bekommt seinen eigenen Fall:

| Test | Deckt ab |
| ---- | -------- |
| `migrationsRunSuccessfullyThroughV11` | AC 5 — `flyway_schema_history`, ≥ 11 erfolgreich |
| `recurringExpensesTableHasAllColumnsWithCorrectTypes` | AC 2 — `containsOnlyKeys` fängt auch eine *zusätzliche* Spalte |
| `amountIsDecimalWithTwoFractionDigits` | ADR-9 — `numericPrecisionAndScale` → `"10,2"` |
| `idIsIdentityPrimaryKey` | AC 2 |
| `foreignKeyToUsersIsDefined` | AC 4 |
| `payeeKeyIsUniquePerUser` | Dauerhaftigkeit des «Kein Abo» — geprüft wird die Spalten**kombination**, nicht bloss die Existenz irgendeiner UNIQUE |
| `statusAcceptsOnlyDetectedAndDismissed` | AC 2 — `INSERT` mit `status = 'NONSENSE'` muss scheitern. Eine Constraint, deren Wirkung niemand ausgelöst hat, ist unbelegt |
| `allColumnsAreNotNull` | AC 2 |
| `upperCaseComparisonMatchesRegardlessOfStoredCase` | AC 3 — Treffer über `upper(payee_key) = upper(?)` bei gemischter Schreibweise |

Zusätzlich manuell, weil AC 5 es wörtlich verlangt: `docker compose up -d`, dann Anwendungsstart.
Und `scripts/check-migrations.sh` gegen `origin/main` als Gegenprobe zur Versionswahl.

Kein E2E- und kein Unit-Test: Die Migration enthält keine Java-Logik, und `docs/CONVENTIONS.md:239`
verlangt für Migrationen genau eine Integrationsstufe («jeder Endpoint und jede Migration mind.
1× getestet»).
